# Vibe Zoo wrap-up · 2026-09-09

AI-DLC는 종료 상태를 유지합니다. 이 문서는 현재 구현 정리와 일반 개발 방식의 후속 검토입니다.

## 반영한 변경

- 동료 [PR #1](https://github.com/hjsg1010/vibe-zoo/pull/1)을 `7b0c74c`로 main에 병합했습니다. 동료 브랜치는 수정하지 않았습니다.
- 검증 보고서가 아직 없는 생성 후보도 개별 시험을 접수할 수 있습니다. 원본 생성 작업의 종료·미확인 동작 유무·이전 입력을 확인하며, 접수만으로 활성화하지 않습니다. 개인 Skill은 기존 시연 학습 검증 경로를 사용합니다.
- 연결을 잃은 읽기 전용 Discover 관찰은 중단으로 정리할 수 있습니다. 변경 동작과 업무 사후 조건이 있는 실행은 이 경로로 성공 처리하지 않습니다.
- Keeper에 개인 자산 삭제와 구체적인 시험 입력 오류 안내를 반영했습니다. PR 검토 중 발견한 공유 데이터 삭제 문제를 보완해 Store 게시 스냅샷과 다른 사용자의 설치는 보존합니다. 다른 Skill 또는 진행 중·미확인 작업에서 쓰는 자산은 삭제를 거절합니다.
- 기존 Live Demo의 메일 우선 진입, 확장 아이콘부터 시작하는 말풍선 안내, 7개 메일 도구, 복합 요청, 여러 개인 Skill을 유지했습니다.

## 검사와 증거의 범위

병합 코드에서 타입·린트·87개 테스트·Backend/Extension/Store 빌드·공개 파일 검사가 통과했습니다. [원격 CI](https://github.com/hjsg1010/vibe-zoo/actions/runs/34319501613)도 통과했습니다. 추가 회귀 검사는 미검증 후보 접수의 원본 작업/입력 경계, 타 사용자 삭제 거절, 공유 데이터 보존, 의존 Skill/미확인 작업의 삭제 차단을 다룹니다.

Backend를 새 빌드로 재시작하고 현재 Chrome의 Keeper를 새로고침한 뒤 기존 MinIO 탭에 연결했습니다. 아래 Keeper 이미지는 실제 연결된 Extension에서 캡처한 **후보·삭제·시험 입력 UI**이며, 해당 후보의 검증 성공이나 삭제 실행을 주장하지 않습니다. 기존 자산·Store·MinIO 데이터는 삭제하거나 재생성하지 않았습니다. 이번 wrap-up에서 Bedrock 호출과 이미 통과한 전체 업무 실행을 반복하지 않았습니다.

기존 실제 기능 검증과 동료 환경 결과의 출처는 [README](../README.md#구현과-검증-상태)에 유지합니다. 이번 기능 캡처는 실제 Extension 적용 화면만 사용하며 Live Demo 캡처는 포함하지 않습니다. 캡처는 제품 영역만 잘라 주소창·프로필·로컬 파일을 제외합니다. 성공 문구나 업무 상태를 이미지에 덧그리지 않습니다.

반도체 YMS는 사용자가 제공한 실제 WaferSight 데모 웹페이지에 Chrome Extension을 연결해 캡처했습니다. 자동 도구 준비의 실제 페이지 관찰 **1회 / 모델 0회**를 확인했습니다. 현재 모델 전송 허용 범위 밖이므로 생성은 보류되었고, DOM 관찰의 `truncated` 제한도 표시됐습니다. YMS 도구 생성·MCP 업무 실행·Skill 학습 성공으로 표시하지 않습니다. 화면의 측정값·알람은 해당 사이트가 표시한 데모 데이터이며 Vibe Zoo가 생성하거나 변경한 값이 아닙니다.

공개 영상은 아직 없습니다. 기능별 촬영 입력과 초기 상태는 기존 README의 촬영 순서를 재사용합니다. Release `v0.1.1` ZIP은 이전 배포물이며 이번 PR의 수정은 main 소스에서 빌드해야 반영됩니다.

## 후속 검토: Discover와 Skill의 역할

사용자가 설명한 기대가 기준입니다. **Discover는 페이지의 여러 업무 기능을 Agent가 호출할 수 있는 Tool/MCP로 준비하는 과정**입니다. 기본 Skill과 사용자가 가르치는 개인 Skill은 그 도구를 이용하는 후속 단계입니다. 사이트가 Native WebMCP를 제공해야 하는 것은 아닙니다.

현재도 실제 Tool과 Skill의 자료형·실행 경로는 분리되어 있습니다. 다만 생성 범위를 한 작업으로 제한하고 그 작업을 그대로 감싼 기본 Skill을 함께 만들어, 체험상 둘이 비슷해 보입니다. 문구만 바꾸어 해결할 차이는 아닙니다.

| 코드에서 확인한 현재 상태 | 기대와의 차이 |
|---|---|
| [생성 프롬프트](../src/backend/generation/prompts.ts)는 `one reusable browser tool`과 작은 작업 하나를 요구 | 페이지의 다양한 기능 목록을 추출하지 않음 |
| [생성 스키마](../src/shared/asset-schema.ts)의 `generatedBundleSchema`는 단일 `tool` + `basicSkill` | 여러 독립 Tool 후보·개별 준비 상태를 반환할 구조가 없음 |
| [ToolGenerator](../src/backend/generation/tools.ts)는 관찰 한 번, 모델 제안 한 번, 도구/Skill 한 쌍 검증 | 목록·상세·폼 등 여러 화면의 기능 탐색이 없고 생성/Skill 단계가 결합됨 |
| 기본 Skill은 생성 Tool 하나를 호출하는 단일 단계로 구성 | 여러 Tool을 이용하는 업무 절차와 구분이 약함 |
| 준비된 snapshot이 하나라도 있으면 생성 종료 | 기존 도구를 재사용하면서 빠진 기능을 추가 발견하는 경로가 없음 |
| [관찰기](../src/extension/observer.ts)는 현재 DOM에서 최대 180개 요소 수집 | 현재 화면 밖의 기능을 파악했다고 주장할 수 없음 |
| [MCP 서버](../src/backend/mcp/server.ts)와 [Agent](../src/backend/model/agent.ts)는 여러 자산 등록·목록·반복 호출 지원 | 핵심 제한은 MCP 자체보다 Discover 생성 범위/상태 모델에 있음 |
| [SkillLearner](../src/backend/generation/skills.ts)는 준비 Tool + 시연 + 명시적 의도로 절차 구성 | 후속 구현에서 재사용할 기반이 있음 |

Tool은 `메일 검색`, `본문 읽기`, `별표 설정`처럼 독립적으로 호출·검증할 수 있는 기능입니다. 한 Tool의 어댑터 안에 여러 클릭과 입력이 있어도 됩니다. Skill은 예를 들어 `구매팀 메일 검색 → 본문 확인 → 별표 설정 → 결과 정리`처럼 Tool들을 업무 의도·변수와 연결한 절차입니다. 모든 클릭을 별도 MCP Tool로 쪼개는 것이 목표는 아닙니다.

### 권장 개발 순서와 완료 조건

1. **여러 기능 발견:** 현재 페이지 근거에서 기능 후보 목록을 만들고, 필요한 상세/폼 화면만 제한된 예산으로 추가 관찰합니다. 기존 호환 Tool은 재사용하고 미발견·관찰 불가 범위는 표시합니다.
2. **Tool별 준비:** 계약·실행 어댑터·validator·관찰 근거를 후보마다 저장합니다. 실제 MCP `tools/list`·`tools/call` → 요청자 탭 실행 → 사후 상태 확인을 거친 Tool만 활성화합니다. 하나의 실패가 다른 준비 Tool을 가리지 않아야 합니다. 입력 없는 조회는 무의미한 가짜 입력을 추가하지 않고 별도의 실제 상태 검증 기준을 정해야 합니다.
3. **Skill을 후속 단계로 분리:** 준비 Tool에 기본 Skill을 구성하거나 Record·명시적 의도로 개인 Skill을 만듭니다. Skill 검증/저장 상태와 Tool 준비 상태를 따로 표시합니다. 기존 Skill 실행기·변수 매핑·버전·사용자/탭 경계를 재사용합니다.
4. **작은 실제 흐름으로 확인:** 허용된 합성 MinIO에서 서로 다른 기능 최소 3개(목록 조회·생성·상세 확인 등 실제 관찰 가능한 기능)를 준비합니다. Tool 목록 확인·개별 새 입력 검증·2개 이상을 이용한 채팅/Skill·Record 학습·부분 실패 표시·기존 자산 재사용을 완주합니다. 최종 기능은 관찰 근거에 따라 결정합니다.

이 항목은 **코드 검토와 후속 제안**이며 다중 Tool Discover를 구현·실증했다는 기록이 아닙니다. 현재 실제 Backend의 모델 전송 허용 범위는 합성 MinIO로 제한되어 있고 Live Demo의 메일/WaferSight 지원과 다릅니다. 기존 운영 환경이나 모델을 바꾸지 않고 일반 개발로 이어갈 수 있습니다.
