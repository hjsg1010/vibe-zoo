# Vibe Zoo 제약사항과 설계 결정 항목

- 기준일: 2026-09-08
- 함께 읽을 입력: [vibe-zoo-requirements.md](vibe-zoo-requirements.md)
- 제품 방향은 확정되어 있다. 아래 미정 항목은 이를 구현할 기술 선택이다.

## 1. 개발 방식

### 1.1. 해커톤 우선순위

- 최우선은 **확정된 요구사항대로 실제 동작하는 제품과 핵심 시나리오의 완주**다. 문서의 양, 아키텍처의 복잡성, 운영 수준의 완성도를 먼저 늘리지 않는다.
- DB 보안 고도화, 운영용 권한 체계, 고가용성·재해복구, 장기 유지보수와 확장성 설계 등 실제 서비스 운영을 위한 고려는 이번 범위에서 제외한다.
- 심사에 필요한 기본 품질은 유지한다. 키를 코드에 넣지 않는 설정 분리, 데모에 필요한 최소 인증·실행 권한 확인, 입력 검증, 핵심 경로의 오류 처리, 문제를 추적할 수 있는 간단한 로그를 제공한다.
- 사용자·탭을 잘못 선택하지 않는 실행 경계와 생성 결과 검증은 제품이 의도대로 동작하기 위한 요구사항이다. 운영 보안 고도화와 구분한다.
- 기술·문서·테스트는 동작 구현, 재현 가능한 실행, 심사 증거에 필요한 수준으로 정한다. 선택형 AI-DLC 확장도 이 범위에 맞춰 검토하며, 제외한 운영 요건을 필수 개발 범위로 다시 추가하지 않는다.

### 1.2. AI-DLC 진행

- 해커톤 일정은 1박 2일, 참여자는 5명이다. 이 정보만으로 기존 프로젝트의 유닛 분할이나 담당자를 복사하지 않는다.
- **AWS AI-DLC v1.0.1**을 적용한다. 루트 `CLAUDE.md`와 `.aidlc-rule-details/`는 제공된 v1.0.1 규칙 원본이다.
- 개발 에이전트는 **OpenAI Codex**, 모델은 **gpt-6-astra**, 추론 수준은 **ultra**다. 이는 개발 도구 선택이며 Vibe Zoo 제품 Backend의 모델 공급자를 정한 것이 아니다.
- 다른 모델·추론 수준으로 자동 대체하지 않는다. 해당 실행 환경에서 지원 여부를 확인하고 문제가 있으면 구체적으로 보고한다.
- 요구사항 입력은 `requirements/`, AI-DLC가 생성할 단계별 산출물·상태·감사 기록은 `aidlc-docs/`에 둔다.
- 제품 방향에 대한 사용자 승인을 시작 입력으로 존중한다. 아직 만들어지지 않은 설계·구현 산출물이나 확장 규칙 opt-in이 승인되었다고 기록하지 않는다.
- 질문은 실제 미해결 사항에 한정하고, 선택을 요청할 때 구체적인 대안·영향·추천을 준비한다.
- 규칙 상세 파일은 원본을 유지한다. Codex가 핵심 규칙을 읽을 수 있도록 최소 `AGENTS.md`를 둔다.

### 1.3. 사용자 질문과 방향 변경의 구분

- 작업 중 사용자가 묻는 질문은 기본적으로 **설명이나 이해를 위한 순수 질문**이다. 가능성·대안·이유를 물었다는 사실만으로 요구사항, 설계, 구현 방향, 승인 상태를 바꾸지 않는다.
- 질문에는 답하고 기존에 승인된 작업을 이어간다. 질문에 대한 설명이나 Agent의 추천을 사용자 승인으로 기록하지 않는다.
- Inception 또는 Construction 중 변경을 지시하는 발언이 기존 요구사항·승인된 결정과 충돌하거나 다른 목표를 요구하면, 사람의 실수 가능성을 고려해 기존 결정과 새 지시의 차이·변경 영향을 짧게 제시하고 재확인한다. 단순한 가정·대안 질문은 변경 지시로 취급하지 않는다.
- 재확인 전에는 해당 변경에 의존하는 수정만 보류하고, 충돌하지 않는 기존 승인 작업은 이어간다.
- 사용자가 명확히 변경 의도를 확인한 뒤에만 요구사항·계획·설계·코드와 감사 기록에 변경을 반영한다. 이 규칙은 모든 질문마다 승인을 받으라는 뜻이 아니다.

## 2. 제품 실행 경계

- MVP는 웹앱을 대상으로 하는 Chrome Side Panel Extension을 기본으로 한다. Edge 호환성은 실제 지원 API와 테스트로 확인하며 PC 단독 앱은 후속 확장이다.
- 일반 사용자는 별도 하네스·CLI·Agent 앱을 직접 켜고 연결하지 않아야 한다.
- 기본 관찰·실행 대상은 **요청한 사용자가 이미 사용 중인 브라우저 탭**이다. Backend가 별도 브라우저를 열면 로그인 상태가 따라올 것이라고 가정하지 않는다.
- Extension은 단순 표시 UI만이 아니다. 페이지 관찰, 사용자 시연 기록, 지정 브라우저 작업 수행과 결과 전달을 맡는다.
- Backend는 MCP 생성, 기본·개인 Skill 생성, 채팅/Agent 처리, MCP 실행 연결, 자산·작업 상태 저장을 수행할 수 있어야 한다.
- Backend의 논리 역할마다 별도 서버·컨테이너가 필요한 것은 아니다. 사용자별 Kubernetes 컨테이너나 특정 하네스를 전제로 고정하지 않는다.
- Native WebMCP 지원, 서비스 개발팀 코드 수정, 공개 REST API, 관리자 사전 URL 등록을 전제로 삼지 않는다.
- 실제 MCP 연결과 브라우저 실행까지 검증한다. 도구 JSON이나 모의 화면만으로 완료를 선언하지 않는다.

## 3. 관찰·어댑터 기술검증

초기 지원 범위는 대표 데모 흐름에서 관찰한 결과로 정한다. 아래 항목은 관찰 가능 범위와 실패 이유를 확인하기 위한 검토 대상이며, 모든 종류의 페이지·프레임 지원을 이번에 구현해야 한다는 뜻은 아니다.

- SPA 페이지 이동과 탭·문서 수명 변화.
- 동일 출처 및 교차 출처 iframe, 접근 권한이 없는 프레임.
- 표준 폼·버튼과 비표준/canvas UI, 접근성 정보가 부족한 화면.
- Chrome 내부 페이지 등 Extension이 관찰할 수 없는 영역.
- 로그인 만료, 권한별 화면 차이, 목록/상세/빈 화면의 차이.
- 동작을 수행했지만 결과 확인이 실패한 경우와 부분 완료.
- 생성 어댑터를 브라우저에 전달하고 실행하는 방식 및 Extension 배포 방식.

지원 불가 상황은 설명 가능한 결과다. 접근할 수 없는 영역을 지원되는 것처럼 추측하지 않는다.

생성 코드를 임의로 `eval`하거나 중앙 서버의 임의 코드를 그대로 주입하는 구조를 먼저 확정하지 않는다. MV3 실행 환경과 목표 배포 방식에서 가능한 표현·실행 경계를 실제로 검증한다. 구조화된 동작 계획이라는 이름만으로 모든 배포 제약이 해결된다고 가정하지 않는다.

OpenTabs는 사용자 브라우저 연결과 어댑터 접근의 기술 참고 자료다. 특정 구현을 그대로 채택하거나 중앙 Backend에 무수정 이식할 수 있다고 결정한 상태는 아니다.

- [OpenTabs 저장소](https://github.com/opentabs-dev/opentabs)
- [Chrome MV3 요구사항](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)

## 4. 사용자·세션·데이터 경계

- 요청에는 올바른 사용자, Extension 연결, 탭, 문서/페이지 상태, 출처, 실행 작업과 자산 버전을 연결한다.
- 다른 사용자의 브라우저·대화·계정으로 작업을 대체하지 않는다.
- 설치 가능한 자산과 실행 권한·로그인 상태는 별도다. 공유받은 자산도 자신의 환경에서 검증한다.
- 비밀번호, 토큰, 쿠키, 인증 헤더와 개인 브라우저 프로필을 생성 자산에 포함하지 않는다.
- Record와 관찰 데이터는 필요한 범위만 수집한다. 민감 입력 제외와 전송·저장·삭제 경계를 설계한다.
- 자산의 공유는 사용자가 선택한다. 원본 시연 데이터·개인 대화·인증 정보가 함께 공개되지 않게 한다.
- 현재 저장소는 public이다. 사내 호스트, 실제 업무 데이터, 내부 대화 원문, 개인 로컬 경로, 런타임 식별자와 자격증명을 코드·문서·로그·Git에 기록하지 않는다.
- 예시와 공개 테스트는 합성 데이터 및 일반 예시 도메인을 사용한다. 실제 시연 환경 주소와 계정은 저장소 밖에서 주입한다.

## 5. 품질·성능·개선

- 준비된 자산이 있으면 불필요한 전체 재탐색을 하지 않는다.
- 현재 사이트와 요청에 필요한 도구·Skill을 선택적으로 제공한다.
- 탐색 시간·행동 수·토큰·재시도에 상한과 취소를 설계한다.
- 긴 추출이 일반 채팅을 계속 막지 않도록 작업 상태와 동시 처리 방식을 설계한다.
- Backend는 필요한 기능을 수행하면서 가볍게 시작한다. CPU/RAM/GPU 사양을 근거 없이 선확정하지 않는다.
- 대표 흐름의 대기 시간과 토큰 사용은 데모 완주와 사용자 피드백에 필요한 정도로 확인한다. 별도 부하 시험, 상세 자원 벤치마크, 운영용 정량 목표 수립을 선행 필수 작업으로 만들지 않는다.
- 실행 성공은 업무의 사후 상태로 검증한다. HTTP 200이나 예외 없음만으로 성공을 판정하지 않는다.
- 개선 후보는 재현된 실패와 관련 성공 사례를 재검증하고 버전별 결과를 보존한다.
- 점수·효율 개선 수치를 발표할 경우 실제 측정 조건과 표본을 제시한다. 모의 시안의 값은 실측으로 사용하지 않는다.
- 테스트는 핵심 전체 흐름, 새로운 입력, 실패·취소와 잘못된 세션 방지를 검증하는 데 우선 사용한다.

## 6. AI-DLC에서 정할 기술 선택

| 미정 항목 | 결정에 필요한 근거 |
|---|---|
| Backend 언어·Agent 엔진·SDK/하네스 | 생성·학습·다단계 실행·취소·상태 관리의 작은 전체 흐름 |
| 제품 모델 공급자와 호출 방식 | 모델 접근성, 도구 사용 품질, 지연, 비용 |
| MCP transport와 Browser Bridge | 실제 검색·호출, 사용자/탭 라우팅, 재접속 |
| 어댑터 표현·검증·실행 방식 | 일반 사이트 입력 변경, MV3와 배포 경계, 실행 결과 |
| Recorder 수집 신호 | 필요한 관찰 근거와 개인정보·오버헤드 |
| 작업 큐·worker·격리 | 긴 생성 작업과 채팅의 동시 실행, 필요한 코드 실행 범위 |
| 자산·설정·작업 저장소 | 버전, 개인/공유 경계, 재접속과 취소 일관성 |
| Store 구현 | 간결한 게시·탐색·설치와 사용자별 재검증 |
| 사이트·프레임 초기 지원 행렬 | 실제 관찰과 실행 테스트 |
| 데모 실행 환경·사양 | 핵심 흐름을 실행하는 데 필요한 최소 구성과 설정 |

추천은 하나의 가벼운 Backend에서 논리 역할을 나누고 필요한 작업만 별도 worker로 분리하는 출발점이다. 추천을 이미 승인된 기술 결정으로 기록하지 않는다.

## 7. 시작 저장소의 의미

시작 저장소에는 AI-DLC 핵심 규칙, 상세 규칙, 확정된 요구사항·제약사항과 Codex용 최소 `AGENTS.md`를 둔다. 추가 참고 자료는 `reference/mockups/`의 사용자 경험·시스템 구조 HTML 두 개로 한정한다.

HTML의 추출·학습·채팅·공유는 모의 동작이다. 이를 기존 제품 코드나 실제 연동 완료로 간주하지 않고, 구현 코드가 없는 새 프로젝트로 시작한다.

`aidlc-docs/`의 설계·상태·감사 기록은 사용자가 새 세션에서 AI-DLC를 시작한 뒤 생성한다. 애플리케이션 코드와 테스트 디렉터리도 해당 개발 단계에서 생성한다.

이전 프로젝트의 구현 코드, 원본 탐색 기록, 다른 서비스 요구사항과 조직별 작업 분담은 승계하지 않는다.

## 8. 심사 기준과 제출 증거

사용자가 제공한 심사 기준은 6개 항목, 총 100점이다. 아래 항목명은 전달된 설명을 요약한 것이며, 제공되지 않은 항목별 배점을 임의로 정하지 않는다. 어떤 AI 도구를 썼는지보다 실제 결과와 결정의 연결을 보여준다.

| 심사 관점 | 구현·제출에서 보여줄 증거 |
|---|---|
| AI와 개발 단계의 연결 | 요구사항에서 내린 결정이 설계·구현·검증에 반영된 흐름. 단계별 산출물과 실제 변경의 연결을 AI-DLC 기록으로 확인할 수 있어야 한다. |
| 문제 정의 | 누구의 어떤 업무에서, 언제·얼마나 반복해서 불편이 생기는지와 Vibe Zoo가 해결하는 방식을 구체적으로 설명한다. 확인하지 않은 빈도·효과 수치를 사실처럼 만들지 않는다. |
| 구조적 차별성 | 기존 도구와의 차이가 설계와 코드에 드러나야 한다. 현재 사용자 탭을 관찰해 실행 도구를 생성하고, 시연·의도로 Skill을 만들어 재사용하는 구조를 실제 구현과 연결한다. |
| 동작 완성도 | 의존성 선언·락파일·진입점·실행 명령·간단한 CI, 주요 예외 처리와 전역 오류 처리, 진입부터 실제 기능까지 이어지는 호출, README의 기능과 일치하는 실행 화면을 제공한다. 핵심 경로에 TODO·빈 함수·성공을 꾸민 스텁을 남기지 않는다. |
| 시작과 사용 경험 | 처음 보는 사람이 설치·실행·필요한 키/계정을 준비하고 핵심 흐름을 끝까지 수행할 수 있어야 한다. 매뉴얼·예시·트러블슈팅과 UI의 다음 행동, 로딩·성공·오류·빈 상태 피드백을 제공한다. |
| 후속 개발의 기본 품질 | 해커톤 수준의 이해 가능한 모듈 구조, 설정 분리, 시크릿 관리, 최소 인증·권한 확인·입력 검증, 간단한 실행·오류 로그를 제공한다. 프로덕션 수준 운영 체계를 추가로 구축하지 않는다. |

### 제출 시 필수 결과

- **실제로 동작하는 제품 화면의 시연 스크린샷을 루트 `screenshots/` 또는 `result/`에 반드시 저장한다.** 실제 구현 이후 생성하며, 참고 HTML이나 만들어 낸 성공 화면으로 실행 증거를 대체하지 않는다.
- README는 구현·검증된 기능, 설치·실행 순서, 환경 설정과 필요한 키·계정, 대표 사용 시나리오, 제약·트러블슈팅을 설명한다. 시크릿 값 자체를 문서에 넣지 않는다.
- 스크린샷과 README가 같은 기능·실행 흐름을 가리키도록 한다. 문서에는 구현되지 않은 기능을 완료된 것처럼 쓰지 않는다.
- 핵심 요구사항이 어느 코드와 검증·시연 결과로 충족되는지 기존 AI-DLC 산출물에서 추적 가능하게 한다. 이 목적을 위해 같은 내용을 여러 문서로 중복 생산하지 않는다.
- 실제 키나 외부 환경이 필요한 기능은 재현에 필요한 설정을 명시한다. 모의 데이터·대체 경로를 사용한 부분은 그 범위를 표시하며 실제 연동으로 주장하지 않는다.
