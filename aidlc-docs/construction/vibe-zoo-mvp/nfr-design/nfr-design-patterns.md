# U-01 — NFR Design Patterns

## 1. 기준과 책임

**상태**: 2026-09-09T01:27:56Z NFR Design 사용자 승인 완료. 제품 구현·검증 전. [승인 NFR](../nfr-requirements/nfr-requirements.md)의 조건을 [승인 기술 기준](../nfr-requirements/tech-stack-decisions.md)에 반영한다. 아래 P-01~07은 설계 참조이며 새 요구사항이 아니다. 기능·상태 정의는 [BR-01~15](../functional-design/business-rules.md)와 [도메인](../functional-design/domain-entities.md), 컴포넌트 배치는 [logical-components.md](logical-components.md)에만 둔다.

한 Node.js Backend의 비동기 작업과 SQLite의 짧은 트랜잭션으로 시작한다. 외부 웹앱의 변경과 DB를 하나의 트랜잭션으로 묶거나 정확히 한 번 실행을 보장하지 않는다. NFR 단계의 고정 읽기 도구 성공은 제품 생성·학습·실패 복구가 구현됐다는 근거가 아니다.

## P-01 — 검증된 신원과 제한된 실행 문맥

팀 운영자가 발급·폐기하는 참여자별 무작위 데모 자격을 사용하고 Backend에는 검증용 해시와 Actor의 사용 가능 상태를 저장한다. 자격은 비공개로 전달하며 로그·공유 자산에 쓰지 않는다. HTTPS 인증 후 발급하는 불투명 세션도 owner·만료·폐기 상태에 결합한다. 매 요청은 이 세션에서 ActorContext를 얻으며 UI의 owner 필드로 권한을 결정하지 않는다.

Extension의 세션 자격은 신뢰된 확장 컨텍스트에서만 접근하는 `chrome.storage.session`에 두고 Content Script에 노출하지 않는다. Store는 같은 Actor에 속하는 Secure·HttpOnly·SameSite 쿠키로 인증하며 변경 요청의 Origin도 확인한다. 로그아웃·자격 폐기는 관련 세션·연결을 무효화하고 이후 전달/저장을 막는다. 대상 웹앱의 로그인 정보는 이 자격과 별개로 사용자 브라우저에 남긴다. 저장소 수명 특성은 [Chrome storage 공식 문서](https://developer.chrome.com/docs/extensions/reference/api/storage)를 근거로 하며 브라우저 재시작 시 재인증할 수 있다.

WSS는 Extension이 시작한다. 허용된 Extension 출처를 검사하고 첫 인증 메시지 전에는 도구·대상·개인 결과를 전달하지 않는다. 인증 대기는 짧은 제한 후 연결을 닫으며 자격을 URL에 넣지 않는다. 메시지별 owner·connection·tab/document·origin·Job/Action·버전·control/binding revision과 만료를 대조한다. 출처 검사는 참여자 인증을 대신하지 않는다. HTTP와 WSS 요청은 스키마·종류·길이를 검사하고 알 수 없는 필드를 거절한다. C-02 내부 메시지도 실제 sender의 탭/문서와 기록 범위를 확인하며 페이지/Content Script의 관찰 신호를 사용자 확인·제어 요청으로 받아들이지 않는다.

C-03이 만든 실행 문맥 참조를 내부 MCP transport에 별도로 결합하고 C-05가 현재 Job과 대조한다. 모델에는 업무 인자만 제공한다. 모델이 actor·tab·버전·실행 권한을 인자로 지정하거나 다른 Job의 문맥을 재사용할 수 없다. 일반 검색은 본인에게 준비되고 활성화된 고정 버전만, 검증 검색은 지정 후보·사례·Job만 노출한다. Store/설정 조회에는 브라우저 탭을 요구하지 않는다. **연결**: NFR-01, BR-01~05·12.

## P-02 — 전달·취소·반영의 순서

C-03의 Job별 직렬 제어 구간에서 취소, 동작 전달 결정, 입력 보완, 결과/활성화 반영을 순서대로 처리한다. 실제 권한·제어 조건은 매번 SQLite에서 검사한다. C-06의 포인터/설정 변경도 같은 DB의 조건부 쓰기로 보호한다. 프로세스 메모리의 검사 결과만 믿고 나중에 무조건 저장하지 않는다.

| 경계 | 원자적으로 검사·기록할 내용 | 외부 동작과 실패 처리 |
|---|---|---|
| 접수 | `(owner, 요청 종류, 중복 키)`의 유일성, 정규화된 입력 지문, JobReceipt와 실행 스냅샷 | 같은 키/같은 입력은 기존 결과, 같은 키/다른 입력은 충돌. 입력 원문·지문은 공개 로그에 남기지 않음. |
| 전달 결정 | 짧은 쓰기 트랜잭션에서 현재 자격·미취소/control revision·binding·고정 버전·확인 범위·남은 예산 검사, ActionExecution과 시도/전달 의도 기록 | 커밋 후 같은 직렬 제어 구간에서 동기적으로 전송 큐에 넣고 구간을 해제. 네트워크 완료/모델 응답을 기다리며 DB 잠금을 유지하지 않음. |
| 취소 | 취소 사실과 증가한 control revision 저장, 미전달 대기 항목 배제 | 전달 결정/큐 삽입보다 먼저 확정된 취소는 새 전달 차단. 전달이 먼저면 이미 진행됐을 수 있어 기존 동작 결과를 확인. |
| 근거 수신 | Action·시도·버전·대상 일치와 중복 receipt 검사, 실행 사실과 사후 판정 분리 저장 | 늦은 근거는 취소 출처와 함께 보존할 수 있으나 새 전달·활성화 권한은 없음. 삭제된 owner/Job의 데이터는 재생성하지 않음. |
| 개인 준비/포인터 반영 | 현재 자격·미취소 제어, 정확한 후보/의존 버전·본인 검증·보고서, expectedCurrent/설정 revision을 한 트랜잭션에서 검사하고 현재/이전 포인터와 결과 기록 | 영향 행이 없으면 최신값과 충돌 반환. 최초 준비는 BR-07, 개선은 명시적 적용까지 만족해야 함. 개인 off와 진행 중 스냅샷은 보존. |

자동 생성은 위 접수 중복 처리와 함께 owner·사이트 적용 범위·생성 목적의 진행 Job을 재사용한다. 다른 탭에서 같은 자동 준비가 요청되면 기존 진행/원래 대상을 보여주며 그 Job의 binding을 바꾸거나 페이지 이동마다 새 생성 작업을 만들지 않는다.

SQLite 쓰기는 `BEGIN IMMEDIATE`와 조건부 갱신/유일 제약으로 구현한다. DB가 바쁘거나 커밋이 실패하면 외부 동작을 보내지 않으며, 이미 보낸 동작의 결과 저장 실패는 성공 응답 대신 미확인으로 남긴다. 커밋 후 전송 전 프로세스가 죽어도 재시작이 자동 재전송하지 않는다. 이 틈은 외부 동작과 DB 사이에서 제거할 수 없는 미확인 경계다. [SQLite 트랜잭션 문서](https://www.sqlite.org/lang_transaction.html)는 쓰기 경계의 근거이며 브라우저의 원자성을 제공하지 않는다.

C-02는 연결된 문서의 실행 직전에 현재 대상·권한·알고 있는 제어 개정·만료를 검사하고 Action 수신/소비를 기록한다. 같은 연결에서 중복 Action을 다시 실행하지 않는다. 연결/문서가 바뀌면 이전 실행 허가를 폐기한다. 취소 메시지보다 이미 실행된 DOM 동작을 취소가 되돌렸다고 표현하지 않는다. 취소 후 허용되는 것은 C-03이 기존 Action과 기대 사후 조건에 묶어 발급한 제한 읽기 관찰뿐이다. **연결**: NFR-03, BR-03~09·11·13~14.

## P-03 — 대상별 순서와 연결 복구

같은 owner·Extension 인스턴스·탭에는 실행 중인 브라우저 동작을 하나만 둔다. 관찰도 다른 변경의 사후 판정을 오염시킬 수 있으므로 실행부터 사후 관찰까지 같은 대상 순서를 점유한다. Record 중에는 시연 범위를 점유해 자동 동작을 보내지 않는다. 확인/입력 대기에는 실행 슬롯을 놓되 다음 동작 전에 체크포인트를 재검사한다. 연결 ID 교체만으로 그 탭에 남은 미확인 동작을 우회하지 않는다.

예상한 SPA/문서 이동은 Action receipt와 새 문서 관찰로 같은 탭·허용 출처의 이동임을 입증한 뒤 binding revision을 갱신한다. 다음 문서는 새로 권한·제어를 검사한다. 이전 documentId를 재사용하거나 단순히 최신 활성 탭으로 작업을 옮기지 않는다. 설명되지 않는 이동·권한 상실·프레임 접근 불가는 대기 사유다. 정상 전체 문서 이동의 확인 구현은 Code Generation의 실제 검증 대상이며 임시 probe의 SPA 결과만으로 지원 처리하지 않는다.

WSS와 명령 라우팅은 C-02 Service Worker가 소유하고 Panel 수명과 분리한다. 활성 작업/Record/Panel 연결이 필요할 때만 연결과 heartbeat를 유지한다. Worker 종료·브라우저 종료·재연결에 대비해 최소 접수 참조는 session 저장소, 업무 상태는 Backend DB를 기준으로 복원한다. 전역 변수나 heartbeat를 영속성의 근거로 쓰지 않는다. Chrome 116 이상의 WebSocket 수명 특성과 종료 가능성은 [공식 lifecycle 문서](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)에 따른다. 임시 probe는 Panel 소유 연결이었으므로 이 구조의 수명 검증은 아직 남아 있다.

| 재개 시점 | 공통 처리 |
|---|---|
| Panel 재열기 / 통신 재연결 | 인증 후 저장된 JobView를 조회. 과거 binding은 기록으로만 읽고 현재 원래 대상 재확인. 이벤트 유실/순서 변경은 최신 revision 조회로 복구. |
| Backend 재시작 | live 연결과 메모리 슬롯은 복원하지 않음. 진행 중 모델 요청은 결과 불명으로, 전달된 Action은 확인 필요로 둠. 취소·버전·예산은 DB 값 유지. |
| 전달된 변경의 결과 유실 | 새 대상 허가 아래 같은 Action의 기대 사후 상태만 관찰. 수행 확인은 완료 단계 재사용, 미실행이 충분히 확인되면 새 시도, 불명확하면 계속 미확인. |
| 취소/실패 후 재요청 | BR-09를 적용하고 취소 Job은 새 연결 Job으로 접수. 입력 보완은 BR-10의 같은 Job/후보/revision으로 이어가며 새 학습·완료 단계 재실행을 만들지 않음. |

**연결**: NFR-03·05·06, BR-02~03·08~10·15.

## P-04 — 예산을 소유하는 제한 모델·작업 루프

C-03이 Job의 시간·모델 요청·입출력 토큰·브라우저 동작·재시도 예산을 저장하고 호출 전에 예약한다. 초기 값은 [승인 NFR 5절](../nfr-requirements/nfr-requirements.md#5-작업-일관성과-초기-예산)만 참조한다. SDK 내부 재시도는 1 attempt로 두고 C-03이 허용된 일시 오류의 추가 요청을 예산 안에서 결정한다. 인증/권한/입력 오류·모델 변경은 자동 재시도/대체하지 않는다. 요청 중단이나 usage 유실은 비용 0으로 계산하지 않고 예약량을 보존한다.

동일 Job의 모델 요청은 순서대로 수행하고 응답마다 현재 제어를 다시 확인한다. 모델 요청·도구 결과 왕복·검증 제안도 호출 수에 포함한다. 능동 구간 시작을 DB에 기록하고 종료 때 경과를 누적한다. 장애로 열린 구간이 남으면 재개 시 경과를 보수적으로 소진 처리하며 대기 전환은 명시적으로 기록한다. 입력 보완·재접속으로 예산을 초기화하지 않는다. 취소 뒤 기존 Action의 확인도 남은 능동 시간·예약된 읽기 횟수 안에서만 수행한다. 새 변경 전에 결과 관찰의 예산을 남기며, 시간까지 소진되면 새 관찰 없이 미확인 결과를 표시한다.

한 서버에서 생성/학습/개선의 배경 모델 슬롯 1개와 채팅/기존 Skill 실행용 슬롯 1개로 시작한다. 사용자의 수에서 처리 용량을 추정한 값이 아니라 긴 생성이 채팅 슬롯을 독점하지 않기 위한 초기 구현 설정이다. 대기 Job은 DB에 두고 owner별 순환으로 선택한다. 사용자 확인·연결 대기 중에는 모델 슬롯을 잡지 않는다. 실제 계정 할당량이 동시 요청을 막으면 오류와 관측값을 기록하고 값을 조정하며 원활한 동시 실행을 검증했다고 주장하지 않는다. 별도 worker/Redis/분산 큐는 추가하지 않는다.

Bedrock 연결은 Backend `.env`의 AWS_BEARER_TOKEN_BEDROCK·AWS_REGION·BEDROCK_MODEL_ID만 사용한다. ANTHROPIC_MODEL은 무시한다. 필수 설정이 비면 모델 경로만 설정 필요로 표시하고 키를 채팅으로 요청하지 않는다. C-03/C-04의 모델 호출은 같은 Gateway와 예산 검사를 통과한다. 일반/도구 응답을 스키마로 검사하고, 도구 요청은 실제 MCP 실행 후 정제한 성공/실패/미확인 결과를 원래 toolUseId에 연결한다. 모델의 완료 문구는 검증기를 대신하지 않는다. 이 책임 분리는 [Bedrock client-side tool use](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-client-side.html)를 따른다.

**연결**: NFR-04·07, BR-03~06·08.

## P-05 — 생성 계획과 실제 검증의 분리

도구 생성은 고정 MinIO 도구 목록을 반환하지 않는다. C-04는 관찰 근거로 입력 계약·제한된 실행 계획·사후 조건·기본 Skill을 제안하고 C-03/C-06이 여섯 요소와 특정 버전을 연결한다. 구조화된 계획의 명령은 패키지에 포함된 관찰·입력·클릭·선택·제한 대기/이동 기능으로만 해석한다. 임의 JavaScript, eval/Function, 원격 코드 import, 셸 실행을 명령으로 받지 않는다. 단계 수·반복·선택 결과 수·대기와 인자 크기를 제한하며 읽기 폴링도 브라우저 예산에 포함한다.

C-05는 계획 스키마·변수 연결·의존 버전·지원 동작·변경 분류를 실행 전에 검사한다. C-02가 최종적으로 대상과 민감 요소 접근을 거절한다. Locator가 없거나 여러 요소에 맞으면 모델의 확신으로 임의 클릭하지 않는다. 접근할 수 없는 프레임/Canvas 등은 관찰된 한계로 반환한다. 이 해석기가 다양한 웹앱을 충분히 지원하는지는 구현 후 확인하며 필요 기능이 표현되지 않으면 후보를 미준비로 남긴다.

검증 사례의 입력·기대 사후 조건·후보/의존 버전은 실행 전에 고정한다. C-05는 동작 receipt와 별도 사후 관찰을 연결해 통과/실패/미확인을 판정한다. 관찰/시연과 다른 입력, Skill의 전체 절차·사후 조건, 개선의 실패 사례와 관련 성공 사례를 기존 BR 기준으로 검사한다. 이미 끝낸 동작은 기존 실행 참조를 이용하며 validate를 이유로 다시 실행하지 않는다. 기능별 부분 준비를 허용하되 도구 통과가 기본/개인 Skill로 전파되지는 않는다. **연결**: NFR-01·03·06·07, BR-04~07·10·13.

## P-06 — 목적별 데이터 투영과 불변 버전

C-02는 비밀번호/인증/숨김·민감 필드 값을 수집하지 않고, 필요한 요소의 허용된 레이블·구조·행동 및 합성 업무 입력만 추린다. 문서·Record·모델 출력은 신뢰되지 않는 자료로 다루며 제어 명령으로 해석하지 않는다. Backend가 입력 스키마와 합성 MinIO 전송 범위를 다시 확인한다. 비밀로 의심되거나 허용 범위를 확인할 수 없으면 해당 자료 전송을 막고 부족한 근거를 알린다. 문자열 마스킹 하나로 모든 민감정보 제외를 보장한다고 하지 않는다.

| 투영 | 포함할 내용 | 제외/접근 경계 |
|---|---|---|
| 실행 제어 | 비공개 owner·binding·Action·revision·정확한 버전/입력 | 실행 검사와 개인 DB에 한정. 모델·공유·로그에서 제외. |
| 모델 입력/도구 결과 | 허용된 관찰 요약·필요한 합성 업무 값·관련 도구/Skill·판정과 한계 | 실제 주소·탭/문서/Job ID·인증값·전체 DOM·미정제 시연 원문/영상·무관한 대화 제외. |
| 개인 자산/근거 | 소유권이 있는 후보/불변 버전·본인 사례/보고서·개인 설정 | owner 조건을 모든 조회/수정에 적용. 다른 사용자의 ID를 알아도 접근 불가. |
| 게시 스냅샷 | 명시 선택 버전과 실행에 필요한 정제 계약/계획·공개 의존성·검증 요약 | 개인 원본 참조·대화·시연·기본값·비공개 사이트 식별자 제외. 필요한 사이트 값은 설치자의 입력/대상에 결합. |

Record는 필요한 행동 단위 신호만 모으고 범위 이탈/단절 때 중단 이유를 기록한다. Stop만으로 학습·재생하지 않는다. 버퍼와 정제 근거의 수신·만료·삭제는 [승인 NFR 보존 표](../nfr-requirements/nfr-requirements.md#보존과-삭제의-초기-제안)를 따른다. 입력/관찰 크기 상한을 넘으면 성공한 완전 기록으로 취급하지 않는다.

자산 버전과 공개 스냅샷은 불변으로 저장하고 개인 설정/현재 포인터는 revision으로 갱신한다. 게시에 필요한 의존 버전도 공유 가능한지 검사하며 개인 근거를 읽어야만 설치할 수 있는 공유본은 만들지 않는다. 비공개 값이 실행 계약에 박혀 있다면 게시 단계에서 조용히 치환하지 않는다. 매개변수화 등 실행 의미의 변경은 새 후보·검증을 거쳐 선택하게 하고, 게시 투영은 선택한 실행 버전의 의미를 바꾸지 않는다. 설치의 본인 검증, 개선의 명시적 적용, 이전 버전 복구는 P-02의 저장 경계에서 수행한다. 개인 삭제는 먼저 owner의 작업·접근 개정을 닫고 전송을 중단한 다음 해당 개인 행과 근거를 지운다. 늦은 응답은 폐기하고 이미 공유된 스냅샷/타인 설치본은 별도로 유지한다. 최소 정리 명령과 만료 검사만 두며 장기 보관·운영 감사 체계는 추가하지 않는다. **연결**: NFR-02·08, BR-10~15.

## P-07 — 상태 조회와 설명 가능한 실패

SQLite의 JobView·AssetView를 화면의 기준으로 삼고 진행 알림에는 owner·Job·revision을 결합한다. Panel은 WSS 알림을 받되 재열기/누락/구버전 응답에는 HTTPS 조회로 최신 상태를 복구한다. Store는 같은 API의 조회·제한된 폴링으로 게시/설치 결과를 보여준다. 알림 수신만으로 저장 성공이나 현재 버전 변경을 확정하지 않는다.

오류는 설정/인증·권한, 입력/확인·버전 충돌, 대상/로그인/프레임, 예산/할당량, 연결/서비스, 실행 결과 미확인으로 나눈다. C-03은 알려진 완료 부분·실제 변경·불확실성·가능한 다음 행동만 WorkOutcome으로 반환한다. 사용자 문구와 필드 위치는 [승인 Frontend](../functional-design/frontend-components.md)를 따른다. 공개 로그는 작업 종류·상태·시간·usage·정제 오류 분류만 남기며 실제 ID·본문·주소·SDK 원시 오류는 제외한다. 상세 실행 관계는 인증된 개인 Job 조회에서 확인한다.

**연결**: NFR-05·07·08, BR-06·09·15. 지원 행렬과 제품 테스트는 [logical-components.md의 검증 연결](logical-components.md#5-구현-후-검증과-다음-단계)에 둔다. 선택형 확장 3종은 모두 비활성, 준수 N/A다.
