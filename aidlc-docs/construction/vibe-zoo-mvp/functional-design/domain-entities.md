# U-01 — Domain Entities

**상태**: 2026-09-08T11:39:23Z Functional Design 사용자 승인 완료. 구현·실행 검증 전이며 기술·저장 방식은 미정이다. [계획](../../plans/vibe-zoo-mvp-functional-design-plan.md)의 범위와 [공통 계약](../../../inception/application-design/component-methods.md)을 상세화한다. 아래는 논리 모델이며 테이블·프로세스 수를 뜻하지 않는다.

## 1. 엔터티와 관계

ref는 내부 참조, revision은 변경 충돌을 판별할 논리 값이다. 실제 식별자·주소·사용자 자료는 공개 문서에 기록하지 않는다. 모든 개인 엔터티는 확인된 owner에 속한다. C-03은 작업·대화·연결을, C-06은 자산·버전·검증·개인 관계를 관리한다. C-02는 현재 브라우저 사실을 제공한다.

| 엔터티 | 최소 업무 정보 | 관계·수명 |
|---|---|---|
| Actor | 확인된 사용자 참조, 접근 범위 | ActorContext의 주체. 웹앱의 현재 로그인·권한과 별개이며 다른 사용자의 연결·개인 자산을 인수하지 않는다. |
| Conversation | owner, 대화 참조, 메시지와 작업 참조 | 한 대화에 여러 Job. 연결이 끊겨도 개인 대화는 유지하며 마지막 탭 정보는 새 실행 권한이 아니다. |
| BrowserBinding | owner, Extension 연결, 탭, 문서/페이지 체크포인트, 출처, 관찰 가능 범위, revision, 연결·권한 상태 | BrowserTarget의 현재 확인 상태. Job은 특정 binding revision을 사용한다. 정상 이동도 확인 후 새 revision을 발급하며 이전 허가는 전용하지 않는다. |
| Job / Attempt | owner, 종류, 요청 중복 키, 대화 참조(선택), 대상, 고정 자산/의존 버전·설정 revision·입력, 예산, 제어 revision, 취소 사실 | generation / execution / learning / improvement / install. Job은 사용자 의도 단위, Attempt는 허용된 재시도 단위다. 무응답 재전송은 새 Attempt를 뜻하지 않는다. 생성 초기 버전 없음은 사유와 함께 명시한다. |
| ActionExecution | Job·Attempt·단계 참조, 고정 입력·버전·binding revision, 동작 의도, 전달 상태, receipt, 사후 관찰·결과 | 전달 전 식별하여 응답 단절 후 같은 변경인지 대조한다. 실행 사실과 업무 성공을 따로 보존한다. 임의 웹앱의 정확히 한 번 실행을 보장하는 장치라는 뜻은 아니다. |
| ChangeConfirmation | Job·동작/한정된 동작 묶음, 표시된 대상·변경·입력·버전·binding revision, 응답, 유효성 | 표시된 제안에만 효력이 있다. 새 대상·입력·동작 범위에는 재사용하지 않는다. 사용자의 직접 시연은 기록 동의이지 이후 자동 재실행 확인이 아니다. |
| Observation / Evidence | owner, 출처 작업·동작·대상·버전·입력 사례, 관찰 사실·한계, 비공개 근거 참조, 공개 가능 요약 | Observation은 관찰 사실, Evidence는 검증·생성 판단과 그 사실의 연결이다. 원본 접근권한을 공유 참조에 포함하지 않는다. C-02가 민감 입력을 제외한 뒤 전달한다. |
| RecordingSession | owner, 기록 참조, 대상·범위, 상태, 종료 체크포인트, 필터된 RecordData, 명시적 의도, 제출 revision | 한 번의 Record→Stop→의도와 학습 Job을 연결한다. 이전 시연의 늦은 응답은 새 시연을 덮어쓰지 않는다. 원본 신호·보존기간·삭제 구현은 NFR 단계에서 정한다. |
| Asset / AssetVersion | 자산 참조·소유/출처, 종류, 불변 버전, 적용 범위, 생성 근거, 이전/기준 버전 | 도구 또는 기본/개인 Skill. 계약·어댑터·성공 조건·절차·의존 버전의 의미가 바뀌면 새 후보 버전이다. 변경 중인 하나의 버전을 실행자들이 함께 읽지 않는다. |
| ToolBundle | 도구 계약·어댑터·성공 판정·기본 Skill·근거·버전의 연결 | 공통 계약의 여섯 요소를 연결하는 생성 산출물. 도구별 버전·검증 범위를 식별하며 묶음 전체를 한 번의 성공으로 승격하지 않는다. 기본 Skill도 별도 검증·설정 대상이다. |
| SkillAsset | 기본/개인 구분, 절차, 변수 계약·기본값, 성공 조건, 의존 도구의 특정 버전 | AssetVersion의 Skill 내용. 모든 의존성은 실행 시 해석 가능한 고정 버전이어야 한다. 누락 도구는 후보/미지원으로 남고 Skill 준비를 막는다. |
| ValidationCase / ValidationRun | 사례 종류·입력·기대 사후 조건, 실행자, 대상 범위, 후보·의존 버전, 실행/관찰 참조, 결과·한계 | 사례 종류는 관찰/시연과 다른 입력, 개선 실패 재현, 관련 성공 회귀 등을 구분한다. Run은 실제 실행과 연결되며 ValidationReport로 반환한다. 취소 뒤 보존한 보고서는 자동 활성화 권한이 아니다. |
| PersonalAsset | owner, 자산/설치 출처, 현재·이전 사용 버전, 이름·설명·기본값·enabled, 설정 revision, 본인 검증 참조 | 개인 설정과 현재 버전 포인터. 게시 원본을 덮어쓰지 않는다. 실행 중 Job은 이 포인터를 매 단계 다시 따라가지 않는다. 명시적으로 저장한 off는 생성·검증·개선 적용으로 해제하지 않는다. |
| Publication / Installation | 게시: 공유자·선택 버전·공개 투영·의존성·검증 요약. 설치: 설치자·선택 게시 버전·개인 연결·자체 검증 | 한 게시 버전에 여러 설치자 관계. 설치자의 대화·브라우저·근거는 공유자와 분리한다. 설치 완료와 사용 준비는 별개다. 새 공유 버전이 기존 설치 버전을 바꾸지 않는다. |
| ImprovementProposal | 개선 Job, 기준 현재 버전, 후보 버전, 이유, 실패·관련 성공 사례/보고서, 적용 판단 결과 | 후보의 추가 업무 정보로 별도 물리 저장소를 요구하지 않는다. 적용 선택은 이 후보·보고서·기준 버전 조합을 가리킨다. 후보 준비와 현재 사용 버전 전환은 별개다. |

관계 요약: Actor → Conversation/Job/RecordingSession/PersonalAsset, Job → Attempt → ActionExecution → Observation, AssetVersion → ValidationRun → Evidence, SkillAsset → 의존 AssetVersion, Publication → Installation → 설치자의 PersonalAsset. Job의 현재 제어와 C-06의 버전 반영 판단은 같은 작업·후보·검증 참조로 연결한다.

## 2. 독립 상태 축

아래 값은 의미를 구분하는 논리 명칭이며 전송 enum을 확정하지 않는다. 화면 문구·다음 행동은 [Frontend](frontend-components.md)에 연결한다.

| 축 | 값과 의미 |
|---|---|
| 연결·실행 조건 | 연결 중 / 연결됨 / 단절, 로그인 필요 / 권한 부족 / 대상 불일치 / 실행 조건 충족. 연결됨만으로 웹앱 권한이나 자산 준비를 보장하지 않는다. |
| Job 생명주기 | 접수 → 진행 ↔ 대기 → 종료. 대기는 입력 보완·변경 확인·연결/대상 복구·결과 재확인 등 이유를 가진다. 취소 요청은 새 전달을 차단하는 별도 단조 제어 사실이며 이미 수행한 결과를 지우지 않는다. |
| WorkOutcome | 성공 / 실패 / 중단 / 부분 완료 / 결과 미확인. 성공은 요청 사후 조건 전체를 관찰한 경우다. 부분 완료는 완료한 부분과 남은 부분을 구분할 수 있는 경우다. 이미 완료한 부분 외에 미확인 변경이 있으면 불확실성을 함께 표시한다. |
| 개별 동작 | 준비 / 전달됨 / 실행 확인 / 미실행 확인 / 실행 여부 미확인. 실행 확인이어도 사후 조건을 못 확인하면 업무 결과는 미확인일 수 있다. |
| 자산 검증 | 후보(내용 생성 중) / 미검증(검증할 내용 고정) / 검증 중 / 통과 / 실패 / 미확인. 통과는 해당 owner·버전·의존성·적용/입력 범위에만 유효하다. |
| 자산 적용·선택 | 적용 범위 일치 / 불일치 / 확인 필요, 기능별 준비 / 미준비 / 미지원, 현재 / 이전 / 개선 후보, 개인 on / off. 일부 기능 준비는 묶음의 부분 준비이며 전체 준비와 다르다. |
| 공유·설치 | 개인 전용 / 선택 버전 게시됨; 미설치 / 설치됨. 설치된 버전도 자체 검증 전에는 일반 실행에 준비되지 않는다. |
| Record | 기록 전 → 기록 중 → 종료·의도 대기 → 제출됨. 같은 확인된 탭·허용 출처 내 이동은 새 문서 범위를 확인해 기록한다. 기록 범위 이탈/관찰 불가/연결 단절 시 멈추고 불완전 이유를 남긴다. 새 시연은 새 기록 참조를 쓴다. |

## 3. 전이와 수명 제약

| 사건 | 허용되는 결과 | 상세 규칙 |
|---|---|---|
| 새 업무 접수 | 현재 대상을 확인하고 실행에 필요한 버전·설정·입력 스냅샷을 만든다. 동일 요청은 같은 접수 결과를 돌려준다. | [BR-01~04](business-rules.md) |
| 정상 페이지 이동 | 이동 결과가 허용된 동작과 일치할 때 다음 동작용 binding revision을 갱신한다. 임의 탭/출처 전환은 대기 사유다. | [BR-02](business-rules.md#br-02--대상과-정상-이동) |
| 취소/종료 뒤 결과 도착 | 근거·실제 결과를 추가할 수 있으나 취소 사실을 되돌리거나 자동 활성화하지 않는다. 대상·권한을 확인한 기존 동작 한정의 변경 없는 관찰로 미확인 판정을 갱신할 수 있다. | [BR-08~09](business-rules.md) |
| 실패 후 재요청 | 미확인 동작부터 해소하고 새 Attempt와 현재 제어를 만든다. 취소한 Job의 재실행은 새 연결 Job으로 접수하며 이전 취소를 해제하지 않는다. | [BR-03·08·09](business-rules.md) |
| 최초 검증 통과 / 개선 검증 통과 | 최초 자산은 유효한 결과 반영 후 개인 사용 흐름으로 간다. 개선 후보는 통과 상태로 대기하다 사용자가 적용해야 현재 포인터가 바뀐다. | [BR-07·13](business-rules.md) |

대화·자산·설정·버전·작업 결과는 새로고침·재접속 후 조회한다. 연결의 생존과 분리하며 저장된 과거 대상은 재인증·재확인 없이 실행 허가로 복원하지 않는다. 데이터 전송/저장/삭제의 구체적 경계, 원자성 구현, 보존기간·용량은 NFR Requirements/Design에서 결정한다. 별도 운영 감사 시스템·이벤트 소싱·분산 트랜잭션을 이 모델로 선채택하지 않는다.
