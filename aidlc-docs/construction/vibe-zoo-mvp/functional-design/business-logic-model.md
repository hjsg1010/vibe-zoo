# U-01 — Business Logic Model

**상태**: 2026-09-08T11:39:23Z Functional Design 사용자 승인 완료. [S-01~06](../../../inception/application-design/services.md)과 US-09를 상세화한다. [도메인](domain-entities.md), [BR-01~15](business-rules.md), [상위 메서드](../../../inception/application-design/component-methods.md)를 참조하며 실제 API 경로·엔진·배포는 선택하지 않는다. 아래 절차는 구현 요구이며 실행 완료 증거가 아니다.

## 1. 공통 실행 절차

모든 흐름은 다음 판단을 공유한다. 논리적 검사와 반영 순서이며 특정 queue·DB·트랜잭션 구현을 정하지 않는다.

1. **접수**: C-03이 Actor와 입력을 검사하고 기존 요청 여부를 확인한다. 필요한 경우 C-02 resolveTarget으로 현재 대상을 확인한 뒤 JobReceipt를 반환한다. 긴 작업 동안 UI는 접수/진행을 조회한다. (BR-01~03)
2. **계획 고정**: 사용할 자산·의존 버전·개인 설정을 읽고 실제 입력·사후 조건을 고정한다. 생성 초기에는 관찰 목표와 버전 미지정 사유를 기록하고 후보 저장 뒤 검증할 버전을 고정한다. (BR-04·06)
3. **동작 준비**: 각 단계의 ActionExecution을 식별하고 현재 제어·대상·예산을 검사한다. 변경이면 범위가 고정된 제안/확인을 받는다. 확인 대기 중 대상·입력이 달라지면 실행하지 않는다. (BR-02·03·05)
4. **실제 실행**: 일반 업무는 C-05 discover/call, 검증은 validate의 후보 제한 경로를 사용한다. C-05가 정확한 C-06 버전을 읽어 C-02 execute/inspect로 연결한다. C-04의 추가 관찰/검증 제안도 C-03을 거친다. C-04가 직접 브라우저를 조작하지 않는다. (BR-01·06)
5. **관찰과 다음 단계**: receipt와 업무 사후 관찰을 연결한다. 정상 이동이면 다음 체크포인트를 확인하고, 미확인 변경이면 결과 재확인으로 멈춘다. Skill 다음 단계 입력은 확인한 앞 단계 결과에서 도출한다. (BR-02·04·09)
6. **결과 반영**: C-03/C-06이 최신 작업 제어·정확한 후보/보고서·현재 포인터 조건을 재확인한 반영 경계로 진행한다. 실제 결과 보존, 준비 판정, 현재 버전 전환, 게시를 구분한다. 같은 Job의 대화/화면에 WorkOutcome을 반환한다. (BR-07·08·13·15)

## 2. S-01 — 현재 사이트 준비와 생성

**입력/출력**: ActorContext + 현재 BrowserTarget → 호환 AssetView 또는 생성 JobView. US-01·02.

1. Keeper 열기 → C-03 prepare → C-06 find로 해당 사용자·사이트의 호환 자산을 확인한다. 개인 준비 자산이면 도구·기본 Skill·예시를 표시하고 전체 탐색을 생략한다. 로그인·권한 문제는 자산 존재와 별도로 표시한다.
2. 공유 자산만 있으면 선택 버전과 설치 상태를 표시하고 S-05로 연결한다. 호환 자산이 없으면 같은 Panel에서 중복되지 않는 생성 Job을 시작한다. 관리자 등록·매뉴얼·전용 앱 실행을 요구하지 않는다.
3. C-03 → C-02 observe로 현재 접근 가능한 페이지 근거를 얻고 C-04 generateTools에 필요한 근거만 전달한다. 추가 관찰은 예산·대상 제어를 거치며 변경이 필요한 탐색은 공통 확인 절차를 적용한다.
4. C-04 CandidateOutput을 C-06 saveCandidate로 저장한다. 도구 계약·어댑터·성공 판정·기본 Skill·근거·버전을 연결하고 검증할 기능별 버전/의존성을 고정한다. 계약 JSON만 생성된 상태는 미검증이다.
5. 관찰과 다른 유효 입력 사례를 만들고 C-05 validate의 실제 MCP/브라우저 경로로 검증한다. 기본 Skill은 의존 도구와 자체 업무 흐름을 검증한다. recordValidation 뒤 유효한 기능만 activate로 개인 사용 가능 상태를 반영한다. 최초 준비에 개선 적용 버튼을 추가하지 않는다.
6. 준비된 기능부터 표시하고 나머지 관찰·검증은 한도 내에서 계속한다. 기본 Skill은 개인 설정에서도 조회한다. 누락/미지원 범위와 관찰 한계를 결과에 남긴다.

**분기/복귀**: 접근 불가·로그인·대상 변경은 이유를 표시하고 공통 재확인으로, 검증 실패는 해당 후보로, 한도 도달은 준비된 부분과 종료 이유로 반환한다. 취소 뒤 새 기능을 자동 활성화하지 않는다. MinIO Console과 다른 미등록 사이트는 이 접수·생성 경로를 공유하며 지원 성공은 각각 실제 근거로 판단한다. **규칙**: BR-01~09·15.

## 3. S-02 — 같은 채팅의 다단계 업무

**입력/출력**: 요청 텍스트 + 대화 + 현재 대상 → 같은 대화의 JobView/WorkOutcome. US-03.

1. C-03 submit이 요청을 접수한다. Keeper Agent는 해당 사이트·요청의 개인 설정과 준비된 Skill만 읽고 C-05 discover로 관련 실제 MCP 도구를 찾는다. off·미준비·범위 불일치는 선택하지 않는다.
2. 선택한 Skill/도구·의존 버전과 입력을 고정한다. 필수 입력이 부족하면 해당 필드/의도를 묻고 기다린다. 도구가 없으면 부족한 기능과 S-01 생성/S-03 시연 경로를 제시한다.
3. 공통 절차로 각 MCP 호출→사용자 탭 동작→사후 관찰을 실행한다. 앞 단계 결과에서 다음 입력이 확정되면 필요한 변경 확인을 받는다. 로그인 만료·임의 이동·미확인 결과는 후속 전달을 멈춘다.
4. 모든 요청 사후 조건이 관찰되면 성공, 일부만 끝나면 완료/남은/미확인 부분을 구분한다. 같은 채팅에 업무 결과·실제 변경·근거 요약·다음 행동을 표시한다. 일반 채팅 응답을 브라우저 실행 성공으로 표시하지 않는다.

**분기/복귀**: 입력 오류는 실행 전 수정, 확인 거절은 전달 중단, 실행 중 실패는 해당 단계와 완료 범위를 반환한다. 재개는 7절을 따른다. **규칙**: BR-01~06·08·09·15.

## 4. S-03 / S-04 — 시연 학습과 개인 설정

**학습 입력/출력**: 필터된 RecordData + 직접 입력한 의도 → 개인 Skill 초안/검증 결과/저장된 AssetView. US-04.

1. Keeper의 C-02 record(start)로 현재 수집 범위를 표시한다. 사용자가 시연하고 record(stop)하면 해당 기록의 종료 상태와 의도 입력을 보여준다. 웹앱 업무 종류와 무관하게 사용자가 Stop을 선택할 수 있다.
2. 같은 기록 참조에 비어 있지 않은 의도를 연결해 C-03 startWorkflow(learning)으로 제출한다. 불완전 기록은 관찰된 범위와 부족한 내용을 드러내고, 이전 시연 응답은 새 초안을 덮어쓰지 않는다.
3. C-03은 준비된 도구를 C-04 compileSkill에 전달한다. 절차·변수·기본값·성공 조건·의존 버전을 초안으로 반환하고 C-06 saveCandidate에 보존한다. 누락 원자 기능은 S-01 후보 또는 미지원으로 연결한다.
4. 초안의 실행 가능한 범위와 바꿀 입력을 표시한다. 시연과 다른 입력의 검증 사례를 준비한다. 입력 보완이 필요하면 Job을 대기로 두고 startWorkflow(learning)의 기존 Job·고정 후보·기대 입력 revision이 있는 요청으로 같은 검증을 이어간다(BR-10). 오래된 후보·취소 Job은 거절하고 새 학습이나 재컴파일을 만들지 않는다. 공통 확인/실행 절차로 검증하며 이미 시연한 변경을 Stop이나 초안 표시만으로 반복하지 않는다.
5. 유효한 검증이 통과하면 recordValidation/activate로 개인 Skill 저장·사용 흐름을 완료하고 같은 채팅과 내 Skill에 반영한다. 부족한 의존성·실패·미확인은 초안 상태로 남긴다. 새 필수 ‘개선 적용’ 버튼을 추가하지 않는다.

**설정 입력/출력**: 개인 자산 + 이름·설명·기본값·on/off 변경 + expectedRevision → 저장된 AssetView. US-05.

1. C-03 query(assets)로 기본/개인 Skill, 의존성·호환성·준비·사용 버전과 저장값을 읽는다.
2. 필드 검증 후 changeAsset(settings) → C-06 updateSettings로 저장한다. 충돌이면 최신값을 다시 읽고 미저장 편집과 구분한다. 성공 응답 전 저장 완료를 표시하지 않는다.
3. 새로고침·재접속 때 저장값을 조회한다. 다음 S-02는 변경 기본값을 사용하며 off 자산을 제외한다. 현재 진행 중 Job은 기존 스냅샷을 유지한다. 개인 학습/설정/실행에 Store 게시가 필요하지 않다.

**분기/복귀**: 학습의 대상 단절·취소·미확인 변경은 7절, 근거 부족은 재시연/누락 기능 안내, 설정 오류는 해당 필드 수정으로 반환한다. **규칙**: BR-01~11·15.

## 5. S-05 — 선택 버전 공유와 설치

**입력/출력**: 공유자의 버전 선택 또는 설치자의 공유 버전 선택 → 게시/설치 AssetView와 자체 검증 JobView. US-06·07.

1. 개인 설정의 공유 진입점 또는 별도 Store에서 선택 버전·공개 항목을 확인한다. C-03 changeAsset(publish) → C-06 publish가 접근·공개 가능 범위를 검사해 명시 요청 버전을 게시한다. 생성/설정 저장이 이 호출을 자동으로 유발하지 않는다.
2. Store의 query(catalog)는 설명·작성자·버전·적용 대상·의존 도구·검증 범위/한계를 표시한다. 개인 기록과 인증정보는 이 투영에 포함하지 않는다.
3. 설치자는 특정 버전을 선택하고 C-03 startWorkflow(install) → C-06 install로 자신의 개인 영역에 그 버전과 의존성을 연결한다. 재전송은 기존 설치 결과를 돌려준다.
4. 자기 Keeper와 연결되지 않았거나 로그인/권한이 부족하면 설치 상태는 유지하고 해당 조치를 안내한다. 연결된 자신의 탭에서 후보 제한 검증과 사후 관찰을 수행하여 자기 실행 문맥에 결과를 연결한다.
5. 필요한 검증과 의존성이 충족되면 개인 사용 준비를 반영한다. Store는 설치/검증 상태를 조회하고, 실제 실행은 자기 Keeper의 같은 대화로 이어진다. 공유자의 다른 세션을 사용하지 않는다.

**분기/복귀**: 공개 불가 자료는 게시 전 수정, 누락 의존성·호환성·미확인은 설치됨/미준비와 이유로 반환한다. 공유자가 새 버전을 게시해도 설치자의 고정 선택을 변경하지 않는다. **규칙**: BR-01·04~09·12·15.

## 6. S-06 — 실패 기반 개선과 적용

**입력/출력**: 기준 현재 버전 + 재현 실패/관련 성공 사례 + 선택적 수정·추가 시연 → 개선 후보·버전별 검증 결과·사용자 적용 결과. US-08.

1. C-03 startWorkflow(improvement)가 기준 버전과 실패·관련 성공 근거를 모은다. 재현 근거가 부족하면 필요한 정보를 표시하고, 추가 실행이 필요하면 공통 변경 확인을 적용한다. 수정·추가 시연 자체는 필수가 아니다.
2. C-04 proposeImprovement가 원인·변경 이유·새 후보를 반환하고 C-06 saveCandidate로 저장한다. 현재 사용 포인터는 유지한다.
3. C-05 validate는 실패를 해결하는 사례와 관련 성공 회귀 사례를 모두 실제 실행/관찰로 확인한다. C-06 recordValidation은 버전별 사례·결과를 보존한다. 실패·미확인·취소는 적용 가능으로 승격하지 않는다.
4. 통과 후보에는 현재/후보 버전·변경 이유·검증 범위와 ‘적용’을 표시한다. **사용자가 선택하기 전까지 현재 버전을 유지한다.**
5. 적용 요청은 C-03 changeAsset(activate) → C-06 activate로 연결한다. BR-13의 후보·유효 보고서·expectedCurrent·작업 제어 검사가 성공해야 이후 업무의 기본 포인터를 바꾼다. 응답 유실이면 조회로 반영 여부를 확인한다.
6. 현재 포인터가 이미 바뀌었거나 근거가 달라졌으면 최신 상태와 이유를 보여주고 자동 재적용하지 않는다. 실패한 반영은 이전 정상 포인터를 유지한다. 사용자가 보존한 버전 복구를 선택하면 changeAsset(rollback)으로 BR-14를 적용한다.

**분기/복귀**: 검증 실패는 후보/현재 구분을 유지한 개선 결과, 적용 충돌은 최신 후보·현재 상태, 복구 후 미준비는 재검증 안내로 반환한다. 진행 중 버전·개인 off·공유 게시 버전은 변경하지 않는다. **규칙**: BR-01~09·13~15.

## 7. US-09 — 취소와 결과 재확인

| 사용자 사건 | 조정 절차 | 결과/복귀 |
|---|---|---|
| 취소 | C-03 controlJob(cancel)이 현재 제어에 취소를 반영한다. 계속 실행을 차단하고 이미 전달된 동작은 BR-08의 대상·권한 재확인과 제한 관찰로 사후 상태를 확인한다. | 중단과 실제 완료/미확인 범위를 함께 표시한다. 늦은 후보는 자동 활성화하지 않는다. |
| 단절·로그인 만료·임의 이동 | 제어를 대기로 두고 진행 상황·원래 대상을 유지한다. 연결 복구 후 resolveTarget과 controlJob(reconcile)로 현재 대상·기존 동작 결과를 재확인한다. | BR-09의 수행됨/미실행 확인/미확인에 따라 남은 단계 재개·재요청 가능 여부를 반환한다. |
| 결과 미확인 | 기존 동작의 의도·입력·사후 관찰을 대조한다. 필요하면 변경 없는 추가 관찰로 확인한다. | 관찰된 결과로 판정을 갱신하거나 미확인을 유지한다. 전체 변경을 자동 반복하지 않는다. |
| 실패 후 재요청 | controlJob(retry)가 기존 결과·예산·대상·확인을 검사하고 허용된 범위만 새 시도로 접수한다. 취소 Job은 새 연결 Job을 만든다. | 완료 단계의 중복 실행을 피하고 새 시도/Job과 기존 결과를 연결한다. |
| 늦은 응답·설정/버전 경합 | Job·Attempt·동작·기록·후보·revision을 대조하고 BR-08/11/13에 따라 보존과 상태 반영을 분리한다. | 최신 상태를 조용히 덮어쓰지 않고 충돌·취소 출처를 표시한다. |

위 절차는 S-01~03·05~06의 관련 브라우저 작업에 공통 적용한다. 일반적인 자동 보상이나 사이트간 전면 연쇄를 신설하지 않는다.
