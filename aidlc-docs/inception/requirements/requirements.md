# Vibe Zoo — Requirements Analysis

## 1. 의도 분석과 문서 상태

- **사용자 요청**: 제공된 요구사항·제약사항과 HTML 시안으로 새 Vibe Zoo 서비스를 구축하고, 첫 요청부터 AWS AI-DLC v1.0.1 감사 기록을 남긴다.
- **요청 유형 / 명확성**: New Project / 제품 경험과 MVP 범위는 명확함. 구현 기술은 의도적으로 미정.
- **범위 / 복잡도**: System-wide / Complex — Extension, Backend, 공유 Store에 걸친 관찰·생성·학습·실행과 사용자별 상태를 다룬다.
- **분석 깊이**: Comprehensive. 추적 가능한 수용조건과 실행 경계를 정리하되 1박 2일·5명 해커톤에 필요한 분량으로 제한한다.
- **프로젝트 상태**: Greenfield. HTML/CSS/JavaScript 시안만 있으며 실제 제품 구현은 없다. Reverse Engineering은 생략했다.
- **문서 기준일**: 2026-09-08.
- **승인 상태**: 2026-09-08T09:14:20Z 사용자 명시적 승인 확인. User Stories 계획 수립으로 진행한다. 이 승인이 후속 계획·설계·구현의 승인을 대신하지 않는다.

입력 기준선은 [제품 요구사항](../../../requirements/vibe-zoo-requirements.md)과 [제약사항](../../../requirements/constraints.md)이다. [사용자 경험 시안](../../../reference/mockups/index.html)과 [시스템 구조 시안](../../../reference/mockups/architecture.html)은 흐름과 논리 책임의 참고 자료다. 본 문서는 입력을 구현·검증 관점으로 정리하며, 요약에 의해 원문 요구사항을 삭제하거나 완화하지 않는다. 질문 답변은 [확장 선택 기록](requirement-verification-questions.md), 분석·결정 경위는 [감사 기록](../../audit.md)에 있다.

## 2. 제품 목표와 MVP 범위

Vibe Zoo는 사용자가 지금 사용하는 웹앱을 같은 브라우저의 대화로 이용하게 하는 Chrome Side Panel Extension이다. 준비된 도구가 없으면 현재 페이지를 근거로 실행 가능한 도구와 기본 Skill을 만들고, 사용자의 시연과 명시적 의도로 개인 Skill을 학습한다. 사내 웹앱의 반복 업무를 수행하는 사용자가 주 대상이며, 반복 빈도나 시간 절감 효과의 미측정 수치를 사실로 제시하지 않는다.

기본 경험: **웹앱 방문 → Keeper 열기 → 호환 자산 확인 → 필요하면 생성·검증 → 같은 채팅에서 업무 수행**.

| 우선순위 | MVP에서 보여줄 결과 | 수용조건 |
|---|---|---|
| 핵심 완주 | Preset 없는 현재 웹앱에서 도구 생성, 실제 MCP 호출, 해당 사용자 탭 실행, 업무 결과 확인 | AC-01~04, AC-09~10 |
| 핵심 개인화 | Record + 의도, 개인 Skill 생성, 다른 입력 검증, 설정 편집·저장·재사용 | AC-04~06 |
| 확장 시연 | 특정 버전 공유·설치와 설치자 환경 검증, 실패 기반 개선 후보·회귀 검증·이전 버전 보존 | AC-07~08 |

확장 시연도 현재 MVP에 포함된다. 규모 조정이 필요하면 핵심 경험을 보존하면서 변경 근거와 사용자 결정을 기록한다. 후속 범위는 네이티브 PC 앱, 전 사이트 자율 탐색, 광범위한 여러 앱 업무 연쇄, 대규모 조직 운영이다. Edge 호환성은 실제 API와 테스트를 확인한 범위에서만 주장한다.

첫 실제 전체 흐름 검증 대상은 **MinIO Console**이다. 전용 도구를 숨겨 두고 범용 생성으로 표시하지 않는다. 다른 미등록 사이트도 동일한 추출 요청 경로에 진입해야 한다. 요청 가능성과 모든 사이트·기능의 추출 성공은 별개이며 지원 범위는 실제 관찰·실행 근거로 표시한다.

## 3. 확정된 시스템 경계

| 경계 | 필요한 책임 |
|---|---|
| 사용자와 현재 웹앱 | 사용자가 이미 로그인한 브라우저 탭이 기본 관찰·실행 대상이다. 웹앱의 기존 로그인·권한과 실제 업무 상태를 사용한다. |
| Extension / Keeper | Side Panel의 채팅·진행 상태·Record·개인 설정, 현재 사이트 인식, 페이지 관찰과 지정된 브라우저 작업 수행, 결과 전달을 담당한다. |
| Backend | MCP Generator, 기본·개인 Skill 생성, 채팅 해석과 다단계 Agent 처리, 실제 MCP 검색·호출 연결, 자산·설정·작업 상태 저장을 수행한다. |
| Store | 별도 웹 UI에서 공유 자산 탐색·게시·설치를 제공한다. 개인 학습·업무 수행은 Store 가입·게시 없이 가능해야 한다. |

사용자는 별도 하네스·CLI·Agent 앱을 켜거나 실행 환경을 선택해 브라우저를 연결하지 않는다. 관리자 URL 등록, 사이트 개발팀의 코드 수정, 공개 REST API, Native WebMCP를 진입 조건으로 요구하지 않는다. Native WebMCP 등록은 선택적 출력이다. Backend가 별도 브라우저를 열면 사용자 로그인 상태가 따라온다고 가정하지 않는다.

위 책임은 논리 역할이며 서버·컨테이너 수, 개발 유닛이나 팀 담당자를 확정한 설계가 아니다.

## 4. 기능 요구사항

### FR-01 — 현재 웹앱에서 시작

- Keeper를 열면 현재 사이트와 호환되는 개인·공유 Preset을 확인한다. 있으면 도구·기본 Skill·요청 예시를 표시하고, 없으면 같은 Panel에서 Backend 생성 작업으로 자동 연결한다.
- 미등록 사이트에서도 현재 탭을 기준으로 요청한다. 준비된 자산의 존재와 현재 사용자의 로그인·권한·실행 가능 상태를 별도로 표시한다.

### FR-02 — 생성 상태와 제어

- 탐색·생성·검증 진행, 취소, 실패 이유, 재요청을 같은 Panel에서 제공한다. 페이지 이동마다 동일 사이트·작업을 중복 생성하지 않는다.
- 후보·미검증·실행 가능·지원 불가·부분 성공을 구분하며 전체 탐색 전에 검증된 기능부터 사용할 수 있다.
- 취소된 작업의 늦은 결과를 자동 활성화하거나 생성 개인 자산을 자동 게시하지 않는다.

### FR-03 — 페이지 근거로 MCP와 기본 Skill 생성

- Backend MCP Generator는 요청자의 Extension을 통해 로그인된 현재 탭의 구조와 가능한 행동을 관찰한다. 이름·의미·입력·실행 절차·성공 조건을 그 근거에 연결한다.
- 생성 결과는 **도구 계약 + 실행 어댑터 + 성공 판정 + 기본 Skill + 검증 근거 + 버전**이다. 메뉴 이름이나 JSON 정의만으로 실행 가능 상태를 선언하지 않는다.
- 관찰·시연과 다른 입력으로 재실행해 고정값 재생과 구분한다. 기본 Skill은 Side Panel 개인 자산 설정에도 표시한다. 매뉴얼과 추가 시연은 보조 근거이며 필수 진입 조건이 아니다.

### FR-04 — Keeper Chat/Agent와 실제 실행

- Backend Agent는 현재 요청에 필요한 Skill과 MCP 도구를 선택하고 여러 단계를 수행한다. 실제 MCP 도구 검색·호출이 Extension의 브라우저 실행으로 연결되어야 한다.
- 실행은 요청에 연결된 사용자·기기/Extension 연결·탭·문서·출처에서 수행한다. 결과는 같은 채팅창에 성공·실패·중단·부분 완료로 반환한다.
- 생성 항목·변경값 등 관찰 가능한 업무 사후 상태로 성공을 판정한다. HTTP 성공, 클릭 완료, 예외 없음만으로 성공 처리하지 않는다.
- 부작용 있는 작업은 대상과 변경 내용을 보여주고 필요한 확인을 받는다. 탐색이 몰래 변경 작업을 실행해서는 안 된다. 단절·로그인 만료·권한 부족 시 다른 사용자나 관리자의 브라우저로 대체하지 않는다.

### FR-05 — Record와 의도로 개인 Skill 학습

- Record 시작 → 현재 웹앱 업무 시연 → Stop → 사용자가 의도를 직접 입력 → Extension이 관찰 기록과 의도를 Backend로 전달한다.
- Backend는 절차·바꿀 입력·기본값·성공 조건·의존 도구를 포함한 초안을 생성한다. 시연과 다른 입력으로 검증한 뒤 개인 Skill로 저장해 같은 채팅에서 사용한다.
- 기존 도구로 가능한 시연은 도구를 조합한다. 새로운 원자 기능은 생성 후보로 연결하거나 미지원 단계를 표시한다. 실행 불가능한 문서나 미검증 초안을 준비 완료로 표현하지 않는다.
- 기록 중임과 수집 범위를 표시한다. 기록 신호는 설계에서 정하며 전체 영상 수집을 필수로 가정하지 않는다.

### FR-06 — Side Panel 개인 설정

- 내 Skill과 현재 사이트 적용 자산을 제공하고 이름·설명·기본 입력값 편집, 활성/비활성 변경을 지원한다.
- 의존 도구·호환성·준비 상태·사용 버전을 표시한다. 개인 자산과 설정은 새로고침·재접속 후 재사용할 수 있도록 저장하고 후속 채팅 실행에 반영한다.
- Store 게시 없이 개인 생성·사용을 지원한다. 선택한 자산의 공유 진입점은 개인 설정에 둘 수 있다.

### FR-07 — 사용자간 공유 Store

- 별도 웹 UI로 도구·Skill 탐색·공유·설치를 제공한다. 설명·작성자·버전·적용 대상·의존 도구·검증 범위를 표시한다.
- 설치한 특정 버전은 설치자 자신의 로그인된 환경에서 호환성과 실행을 검증한다. 자산 설치는 로그인·권한을 제공하지 않는다.
- 공유 자산과 개인 계정·세션·대화·원본 업무 데이터를 분리한다. 개인 설정을 Store로 대체하지 않으며 개인 사용보다 후순위로 간결하게 구현한다.

### FR-08 — 검증을 거치는 자기개선

- 재현된 실행 실패, 사용자 수정, 추가 시연을 근거로 실패 원인과 변경 이유를 설명하는 새 도구·Skill 버전 후보를 만든다.
- 해당 실패와 관련된 기존 성공 사례를 재검증하고 버전별 결과를 보존한다. 후보와 사용 버전을 구분하며 미검증 변경을 조용히 적용하지 않는다.
- 변경 실패 시 정상 버전을 유지하거나 이전 버전으로 되돌릴 수 있어야 한다. 모델 파인튜닝·완전 자율 운영은 필수 요구사항이 아니다.

### FR-09 — 연결과 대화의 일관성

- 대화·장기 생성 작업·설치 자산·실제 브라우저 연결을 구분한다. 같은 사용자의 재접속·탭 변경 후 대화와 자산을 이어갈 수 있는 상태 모델을 설계한다.
- 현재 실행 사이트와 탭을 명확히 표시한다. 다른 사이트로 작업을 넘기면 대상 탭의 연결·권한을 별도로 확인한다.
- 사이트간 전면 자동 연쇄는 초기 필수 시연 범위가 아니다. 다른 사용자의 대화·세션을 섞어 연속성을 구현하지 않는다.

## 5. 비기능 요구사항과 제약

아래 NFR 식별자는 기존 제약사항을 추적하기 위해 붙였다. 새 운영 범위를 추가하지 않는다.

| ID | 요구사항과 검증 방향 | 입력 근거 |
|---|---|---|
| NFR-01 | 요청에 사용자·Extension 연결·탭·문서/페이지 상태·출처·작업·자산 버전을 연결한다. 최소 인증·실행 권한과 입력을 검증하고 잘못된 사용자·탭·문서로 실행하지 않는 경계를 확인한다. | constraints 1.1·2·4; FR-04·09 |
| NFR-02 | Record·관찰은 필요한 범위만 수집한다. 민감 입력 제외와 전송·저장·삭제 경계를 설계한다. 비밀번호·토큰·쿠키·인증 헤더·개인 브라우저 프로필을 생성 자산에 포함하지 않고 원본 시연·개인 대화·인증정보를 함께 공개하지 않는다. | constraints 4; FR-05·07 |
| NFR-03 | 취소·단절·로그인 만료·권한 부족·부분 완료·결과 확인 실패를 정확히 구분한다. 취소를 이미 발생한 변경의 자동 복구로 간주하지 않으며 중단된 변경을 재시도하기 전 실제 결과를 확인한다. 취소 후 늦은 결과와 버전 변경이 현재 자산·작업을 잘못 활성화하지 않도록 설계한다. | constraints 3~5; FR-02·04·08·09; architecture 시안의 중단·복구 설명 |
| NFR-04 | 준비된 자산 재사용, 사이트/요청별 도구·Skill 선택, 탐색 시간·행동 수·토큰·재시도 상한과 취소를 설계한다. 긴 생성이 일반 채팅을 계속 막지 않게 한다. 대표 흐름 대기 시간·토큰은 필요한 정도로 측정하며 수치·서버 사양·부하 시험을 선확정하지 않는다. | constraints 5 |
| NFR-05 | 사용자는 같은 Panel에서 다음 행동과 로딩·성공·오류·빈 상태·실행 대상을 이해할 수 있어야 한다. 일반 기능명은 채팅·도구·내 Skill·설정으로 유지한다. Zoo 표현은 캐릭터·설명·상태에 적용하며 사용자는 가르치고 선택하는 사육사, 중앙 Agent는 훈련사로 표현한다. | requirements 6; constraints 8 |

| NFR-07 | 의존성 선언·락파일·진입점·실행 명령·간단한 CI, 이해 가능한 모듈 구조, 설정·시크릿 분리, 주요 예외·전역 오류 처리와 간단한 실행/오류 로그를 제공한다. 핵심 경로를 TODO·빈 함수·성공을 꾸민 스텁으로 남기지 않는다. | constraints 1.1·8 |

운영 DB 보안 고도화, 운영 권한 체계, 고가용성·재해복구, 장기 유지보수·확장성 체계는 범위 밖이다. 별도 부하 시험·상세 자원 벤치마크·운영 정량 목표 수립을 선행 필수 작업으로 만들지 않는다. 이는 NFR-01~08의 기본 품질을 제외한다는 뜻이 아니다.

## 6. 수용조건과 완료 증거

모든 항목은 **구현·실행 검증 전**이다. 아래는 요구되는 증거이며 이미 달성한 결과가 아니다. 이후 User Stories·설계·코드·검증 산출물에서 같은 FR/AC/NFR 식별자를 참조한다.

|---|---|---|
| AC-01 | FR-01·02 | Preset 없는 현재 웹앱에서 Keeper를 열어 관리자 등록 없이 생성 흐름에 진입한다. |

| AC-03 | FR-04 | 실제 MCP 도구 검색·호출이 해당 사용자 브라우저의 실행과 화면/상태 결과 확인으로 이어진다. |
| AC-04 | FR-03·05 | 관찰 또는 시연과 다른 입력으로 재실행해 고정값 재생이 아님을 확인한다. |

AC-06·09의 상세 검증 범위는 기존 FR 및 constraints의 명시 내용을 연결한 것이며 별도 기능을 신설한 것이 아니다. 핵심 전체 흐름·새 입력·실패·취소·세션 경계의 테스트를 우선하고, 공유/개선도 해당 수용조건을 확인한다.

제출 시 실제 제품 화면 스크린샷을 루트 `screenshots/` 또는 `result/`에 저장한다. README에는 구현·검증된 기능, 설치·실행 순서, 환경 설정과 필요한 키·계정의 종류, 대표 시나리오, 제약·트러블슈팅을 설명한다. README와 스크린샷은 같은 실제 흐름을 가리켜야 한다. 모의 데이터·대체 경로를 쓴 범위는 표시하고 연동 완료로 주장하지 않는다.

심사 기준은 입력의 6개 관점, 총 100점을 유지하며 항목별 미제공 배점은 만들지 않는다. 문제 정의, 구조적 차별성, AI와 개발 단계의 연결을 실제 코드·검증 결과로 추적한다. 효율·점수 개선을 발표하면 실제 측정 조건·표본을 함께 제시한다. 같은 추적 정보를 별도 문서 여러 개에 반복 생산하지 않는다.

## 7. 후속 설계·기술검증에서 결정할 사항

다음은 모두 **미정**이며 이 문서 승인으로 특정 기술이 채택되는 것은 아니다. 해당 단계에서 작은 실제 전체 흐름과 기술 제약을 확인한 뒤 구체적인 대안·영향·추천을 제시한다.

| 미정 항목 | 결정 근거 |
|---|---|
| Backend 언어·Agent 엔진·SDK/하네스 | 생성·학습·다단계 실행·취소·상태 관리의 작은 전체 흐름 |
| 제품 모델 공급자·호출 방식 | 실제 모델 접근성, 도구 사용 품질, 지연·비용 |
| MCP transport·Browser Bridge | 실제 검색·호출, 사용자/탭/문서 라우팅과 재접속 |
| 어댑터 표현·전달·검증·실행 | 다른 입력 실행, MV3 환경 및 목표 배포 방식의 허용 경계, 업무 결과 |
| Recorder 수집 신호 | 학습에 필요한 근거, 민감 입력 제외, 전송·저장·삭제 및 오버헤드 |
| 큐·worker·격리 | 긴 생성과 채팅 동시 처리, 필요한 코드 실행 범위 |
| 자산·설정·작업 저장소 | 개인/공유 경계, 버전, 취소·재접속·진행 작업 일관성 |
| Store 구현 | 간결한 게시·탐색·설치와 사용자별 재검증 |
| 사이트·프레임 초기 지원 행렬 | 대표 흐름에서 실제 관찰·실행 가능한 범위와 실패 이유 |
| 데모 설치·접속·배포 환경과 사양 | 핵심 흐름에 필요한 최소 구성, 실제 사용 가능한 환경·설정 |

하나의 가벼운 Backend에서 역할을 나누고 필요한 작업만 worker로 분리하는 안은 입력의 추천이다. OpenTabs 재사용, Git 기반 Store, 공통 MCP 서버, 사용자별 Kubernetes, 특정 하네스는 채택된 기술이 아니다. 임의 생성 코드의 eval·원격 코드 주입을 선확정하지 않으며 구조화된 계획이라는 이름만으로 MV3/배포 적합성을 보장하지 않는다. 공개 Chrome Web Store 배포 적합성도 미검증 상태다.

개발 도구의 Codex / gpt-6-astra / ultra 지정은 제품 Backend 모델 공급자를 결정하지 않는다. 사용자 질문은 기본적으로 설명 요청으로 취급하며, 기존 승인 방향과 충돌하는 변경 지시는 차이·영향을 제시하고 변경 의도를 확인한 후 반영한다.

## 9. 시안 반영 및 검토 요청

- 시안의 개인 Skill 초안 즉시 활성화는 실제 제품에서 다른 입력 검증 후 사용 가능 전환으로 구체화한다.
- 시안의 메모리 설정은 FR-06의 설명·의존성·호환성·버전 표시와 영속 저장을 포함해 구현한다.
- 생성 결과의 네 부분 요약에 검증 근거·버전을 포함하고, 타이머 성공·도구 수량·URL 이름 변경을 실제 연동이나 범용성의 증거로 사용하지 않는다.
- 시안의 박스와 배포 추천을 구현 완료·물리 배치 결정으로 해석하지 않는다. 기존 HTML 원본은 변경하지 않았다.

다음 단계는 **User Stories**다. 신규 사용자 기능, 생성·시연·실행·설치 등 여러 사용자 흐름, 공유자와 설치자, 실패·취소·재접속의 수용 시나리오가 있어 CLAUDE.md의 실행 조건에 해당한다. 요구사항 승인 후 스토리 계획 수립을 시작하며 스토리 생성은 계획 승인 후 진행한다.

승인은 [요구사항 검토 질문](requirements-review-questions.md)의 A 답변과 대화 원문으로 확인했으며 [감사 기록](../../audit.md)에 남겼다. 이후 질문은 사용자의 요청에 따라 대화에서 하나씩 추천과 함께 진행하고 답변 기록은 에이전트가 맡는다. 전체 Workflow Planning 및 설계·구현 승인은 후속 단계에서 별도로 다룬다.
