## 제안하는 구성

**사용자 여정 중심 구성**을 추천한다. 한 스토리는 사용자가 확인할 수 있는 결과 하나를 다루며 필요할 때만 세분화한다. 스토리 개수를 맞추기 위해 분할하거나 수용조건을 생략하지 않는다. 기술 구성요소별 구현 작업·스프린트·일정은 작성하지 않는다.

다음 7개 묶음은 스토리 구성 기준이다. 고정된 스토리 수, 개발 유닛, 서비스 분할 또는 새로운 우선순위 결정이 아니다.

|---|---|---|
| 현재 사이트에서 도구 준비 | Preset 확인, 없으면 생성·검증, 여섯 구성요소와 근거·버전, 미등록 사이트 요청과 지원 범위 | FR-01, FR-02, FR-03; AC-01, AC-02, AC-04, AC-10 |

마지막 묶음에 공통 실패·복구 조건을 한 번 정의하고 관련 스토리에서 참조한다. 개별 업무에만 있는 예외는 해당 스토리에 둔다. 첫 검증 대상 MinIO Console, 다른 미등록 사이트의 동일 요청 진입, 후순위인 Store·개선의 MVP 포함은 승인 입력 그대로 유지한다.

페르소나는 **사내 웹앱 사용자 1유형**으로 충분하다. 업무 실행·시연·공유·설치를 역할로 구분한다. 특히 AC-07의 공유자와 설치자는 같은 유형이더라도 반드시 서로 다른 사용자·세션이다. 이름·나이·직급·사용 빈도·효과 수치를 지어내거나 관리자·운영자를 새 페르소나로 추가하지 않는다.

## 대안과 선택 이유

| 구성 방식 | 장점 | 이번 맥락의 비용·판단 |
|---|---|---|
| User Journey-Based | 사용 시작부터 결과 확인까지의 연결과 시연이 명확하다. | 추천. 공통 실패 조건을 참조해 반복을 줄인다. |
| Feature-Based | FR별 기능 누락 점검이 쉽다. | 실제 업무 흐름이 여러 기능 항목으로 분산될 수 있다. FR 참조로 장점만 보완한다. |
| Persona-Based | 사용자 유형별 목적 차이를 드러낸다. | 주 페르소나 한 유형인 이번 MVP에서는 역할별 문서 중복이 늘어난다. |
| Domain-Based | 사업 도메인별 경계를 드러낸다. | 사이트 도메인을 기준으로 나누면 MinIO 전용 범위로 오해할 수 있다. |
| Epic-Based | 큰 제품 범위의 상하위 구성이 쉽다. | 별도 에픽 계층은 작은 해커톤 범위에 문서 비용이 크다. |

혼합이 필요하더라도 1차 분류는 사용자 여정으로 유지하고, FR/AC 및 역할은 스토리 필드로만 연결한다. 별도 기능별·페르소나별 스토리 사본을 만들지 않는다는 기준을 둔다.

## 형식과 검증 수준

각 스토리는 ID, 페르소나/역할, 사용자 목적과 가치, 전제조건·필요 자산, 관련 FR/AC/NFR, 수용조건으로 작성한다. 수용조건은 짧은 Given/When/Then으로 정상 결과, 필요한 실패 결과, 해당되는 새 입력·사용자/탭 경계를 표현한다. 원문 FR/NFR의 긴 설명은 복사하지 않는다.

INVEST 점검 기준은 다음과 같다.

- Independent: 관찰 가능한 결과 단위로 분리하고 자산·상태 선행조건과 의존 스토리를 명시한다. 자산을 준비한 상태에서 독립적으로 검증할 수 있게 하되 실제 전체 흐름 검증을 대체하지 않는다.
- Negotiable: 구현 방법은 협의 가능하게 두고 승인된 제품 범위를 임의로 축소하지 않는다.
- Valuable: 사용자 목적·이익을 한 문장으로 설명한다.
- Estimable: 시작 조건·완료 상태·지원 범위를 이해할 수 있게 하며 미정 기술을 가짜 확정사항으로 채우지 않는다.
- Small: 한 번에 확인 가능한 업무 결과를 기준으로 필요한 만큼만 나눈다.
- Testable: 화면/업무 상태로 검증하고 HTTP 성공·모의 타이머·JSON 생성만으로 통과시키지 않는다.

기존 NFR-01~08은 각 관련 스토리에서 참조한다. 제출 스크린샷·README·실행/오류 처리·간단한 CI 등 공통 완료 기준은 requirements.md의 5~6절을 연결한다. 개발자 작업을 사용자 스토리로 억지 변환하거나 별도 제출 기준 문서를 만들지 않는다.

## 계획 질문 필요성 검토

| 검토 범주 | 현재 근거와 처리 |
|---|---|
| 페르소나 | 승인된 사내 웹앱 사용자와 공유/설치 역할로 구성 가능. 위 최소안에 포함한다. |
| 스토리 크기·형식 | 사용자 요청의 간결함에 맞춰 결과 하나와 짧은 수용조건으로 제안한다. |
| 분해·그룹 방식 | 여정 중심과 공통 예외 참조를 계획 승인 질문 하나로 확인한다. |
| 수용조건 | 승인된 AC-01~10 및 FR/NFR로 충분하며 범위를 재질문하지 않는다. |
| 사용자 여정 | 준비·실행·학습·설정·공유·개선과 중단/복구를 입력에서 확인했다. |
| 비즈니스 맥락 | 1박 2일·5명, 핵심 완주 우선과 후순위 MVP 범위가 확정되어 있다. |
