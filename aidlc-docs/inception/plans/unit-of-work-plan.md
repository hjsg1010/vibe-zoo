공통 실행·검증·버전 상태를 여러 유닛이 반복 설계할 필요를 줄이고, 같은 유닛의 Code Generation 앞부분에서 첫 실제 흐름을 확인한다. **하나의 개발 유닛은 하나의 서버·프로세스·Backend 물리 모놀리스를 뜻하지 않는다.** Chrome Extension과 Backend, 별도 Store의 제품 경계는 유지하며 기술·엔진·worker·배포는 후속 근거로 정한다.

검토한 대안:

| 대안 | 영향과 현재 판단 |
|---|---|
| Extension / Backend / Store별 유닛 | 독립 배포·소유권이 확정되면 장점이 있다. 현재는 핵심 흐름이 여러 유닛에 걸리고 선행 유닛 완주 전 실제 통합을 미루기 쉬워 추천하지 않는다. |
| 실행 / 개인화 / 공유·개선별 유닛 | 업무 결과는 구분되지만 같은 C-03~06과 상태를 반복 변경한다. 현재는 유닛 내부 구현·검증 순서로 관리하는 편이 간결하다. |

[Units Generation 규칙](../../../.aidlc-rule-details/inception/units-generation.md)은 유닛을 개발 목적의 스토리 묶음으로 정의하고 monolith는 내부 모듈을 가진 단일 유닛으로 설명한다. [Code Generation 규칙](../../../.aidlc-rule-details/construction/code-generation.md)의 multi-unit monolith 경로 예시는 코드 배치 예시로만 참조한다. 이를 근거로 물리 구조를 채택하거나 컴포넌트·참여자 수를 유닛 수로 환산하지 않는다.

## 3. 유닛 안의 구현·검증 순서

아래는 **같은 유닛의 승인된 Code Generation 계획에 반영할 내부 순서**다. 별도 AI-DLC 단계나 각자 설계·코드 승인을 반복하는 가상 유닛을 신설하지 않는다. 앞서 해당 유닛의 Functional Design → NFR Requirements → NFR Design → Infrastructure Design을 실행 계획에 따라 수행한다.

| 2 | Record → Stop → 의도 → 개인 Skill → 다른 입력 검증 → 개인 설정 저장·재접속·재사용 | US-04·05 |
| 3 | 특정 버전의 명시적 게시·다른 사용자의 설치·자기 탭 검증 | US-06·07 |
| 4 | 재현 실패에서 개선 후보·실패/관련 성공 재검증·이전 버전 보존. 수정·추가 시연은 선택적 보조 근거 | US-08 |

최소 실행 구성·오류 처리·설정 분리·필요 테스트는 첫 경로부터 포함한다. 첫 검증 지점 이후 의존 기능을 확대하고, 핵심 기술 가정이 실패하면 해당 설계·코드 계획을 갱신한다. 모든 화면을 먼저 완성한 후 마지막에 MCP를 붙이는 순서로 바꾸지 않는다. 구현 실험은 승인된 Code Generation 안에서 수행한다.

U-01의 전체 코드·필요 검증 완료 후 **Build and Test**에서 전체 설치·핵심 실행·개인화·공유·개선의 통합 재현, README·실제 스크린샷·간단한 CI와 제출 증거를 확인한다. 최종 증거는 requirements.md 6절을 참조하며 여기서 중복 작성하지 않는다. 일정만을 이유로 공유·개선을 완료 범위에서 제외하지 않는다.

## 4. 협업과 Greenfield 코드 조직

5명은 같은 유닛 안에서 승인된 컴포넌트 책임과 공통 계약을 기준으로 독립 구현·검토·검증 작업을 병행할 수 있다. 구체 담당자·개인별 소유권·고정 작업 시간을 가정하지 않는다. 통합 대상과 공통 계약 변경은 현재 유닛에서 조정한다.

코드는 저장소 루트의 단일 유닛 기본형인 **src/, tests/, config/**를 출발 전략으로 두고 Extension·Backend·Store의 논리 모듈을 구분한다. 언어·패키지·빌드/배포 도구가 정해진 뒤 정확한 파일 경로를 Code Generation 계획에서 확정한다. 한 경로 전략을 한 런타임·배포 단위로 해석하지 않는다.

AI-DLC 문서는 aidlc-docs/에만 두고 실제 코드·테스트·설정·스크린샷은 제품 경로에 둔다. 지금 제품 디렉터리나 구현 파일을 미리 만들지 않는다. 독립 배포 서비스 분리의 필요성이 나중에 확인되면 승인 설계·유닛 계획·스토리 매핑의 영향을 검토하고 변경을 반영한다.
